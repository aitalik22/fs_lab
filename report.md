## Задание 3. Исследование inode и размера файла

### Гипотеза

Предполагаю, что при переименовании файла в пределах одной файловой системы:

- Номер inode не изменится.
- Содержимое файла останется прежним.
- Блоки данных не будут скопированы.
- Изменится только имя файла в записи каталога.

### Эксперимент
Для исследования были выполнены следующие команды:

```bash
echo "Hello" > report.txt
stat report.txt
ls -li report.txt
mv report.txt final.txt
stat final.txt
ls -li final.txt
ls -l final.txt
du -h final.txt
touch empty.txt
stat empty.txt
du -h empty.txt
stat final.txt > inode_info.txt
```

### Наблюдение

После переименования файла report.txt в final.txt номер inode остался прежним — 20980. Содержимое файла не изменилось.

Результаты исследования размеров файлов:

| Характеристика | final.txt | empty.txt |
|---|---|---|
| Inode | 20980 | 21481 |
| Логический размер | 6 байт | 0 байт |
| Blocks | 8 | 0 |
| Выделенное пространство | 4096 байт | 0 байт |
| Количество ссылок | 1 | 1 |
| Права доступа | 0644 | 0644 |

Файл final.txt содержит слово Hello и символ переноса строки, поэтому его логический размер составляет 6 байт.

Файловая система выделила 8 единиц по 512 байт:

8 × 512 = 4096 байт.

Пустой файл empty.txt имеет собственный inode, но не содержит данных, поэтому блоки данных ему не выделены.

### Ответы на вопросы

1. Почему переименование в пределах одной файловой системы обычно не меняет inode?

При переименовании изменяется имя файла в записи каталога. Сам inode и блоки данных остаются прежними.

2. Где хранится имя файла?

Имя файла хранится в записи каталога, которая связывает его с номером inode.

3. Почему Size и Blocks измеряют разные характеристики?

Size показывает фактический логический размер содержимого файла в байтах, а Blocks показывает количество выделенных единиц дискового пространства по 512 байт.

### Вывод

В ходе эксперимента установлено, что переименование файла не приводит к созданию нового inode или копированию данных в пределах одной файловой системы. Также было обнаружено, что логический размер файла может отличаться от выделенного дискового пространства. Пустой файл имеет метаданные, но не занимает блоки данных.

Гипотеза подтвердилась.


## Задание 4. Кейс «Исчезнувший отчёт»

### Цель

Исследовать жёсткие и символические ссылки, а также особенности восстановления файлов через Git.

### Гипотеза

Предполагаю, что жёсткая ссылка продолжит работать после удаления исходного имени файла, а символическая ссылка перестанет работать.

| Действие | Гипотеза | Наблюдение |
|---|---|---|
| Прочитать backup.txt после удаления | Файл доступен | Выведено «Отчёт за ноябрь» |
| Прочитать shortcut.txt после удаления | Ошибка чтения | No such file or directory |
| Восстановить report.txt через Git | Символическая ссылка снова работает | Выведено «Отчёт за ноябрь» |
| Сравнить inode после восстановления | Номера inode будут различаться | 21510 и 21533 |

### Эксперимент

Созданы исходный файл report.txt, жёсткая ссылка backup.txt и символическая ссылка shortcut.txt.

Выполнены следующие команды:

```bash
mkdir -p links
cd links
echo "Отчёт за ноябрь" > report.txt
ln report.txt backup.txt
ln -s report.txt shortcut.txt
ls -li
cd ..
git add links
git commit -m "Create hard and symbolic links"
git ls-files -s links
rm links/report.txt
cat links/backup.txt
cat links/shortcut.txt
ls -li links
git restore links/report.txt
cat links/shortcut.txt
ls -li links
cmp links/report.txt links/backup.txt
rm links/report.txt
ln links/backup.txt links/report.txt
ls -li links
```

### Наблюдение

До удаления исходного файла report.txt и backup.txt имели одинаковый inode 21510 и счётчик жёстких ссылок, равный 2.

Символическая ссылка shortcut.txt имела собственный inode 21514.

После удаления report.txt жёсткая ссылка backup.txt продолжила работать, а количество жёстких ссылок уменьшилось до 1. Символическая ссылка стала битой, поскольку её целевой файл отсутствовал.

После выполнения git restore файл report.txt был восстановлен. Символическая ссылка снова стала доступна, однако восстановленный файл получил новый inode 21533.

Команда cmp показала, что содержимое файлов совпадает.

После повторного создания жёсткой ссылки оба файла снова получили общий inode 21510, а количество жёстких ссылок стало равным 2.

| Этап | Inode backup.txt | Inode report.txt | Inode shortcut.txt |
|---|---|---|---|
| До удаления | 21510 | 21510 | 21514 |
| После удаления | 21510 | Отсутствует | 21514 |
| После git restore | 21510 | 21533 | 21514 |
| После повторного ln | 21510 | 21510 | 21514 |

### Объяснение

Жёсткая ссылка является дополнительным именем одного и того же файла. Поэтому удаление одного имени не приводит к потере данных, пока существует другое имя, указывающее на этот inode.

Символическая ссылка хранит путь к файлу. Если файл по указанному пути отсутствует, ссылка становится битой.

В выводе git ls-files -s обычные файлы имеют режим 100644, а символическая ссылка — 120000.

Git сохраняет содержимое файлов и символические ссылки, но не сохраняет отношения жёстких ссылок между файлами.

### Вывод

В ходе эксперимента я изучил различия между жёсткими и символическими ссылками. Установлено, что жёсткая ссылка позволяет сохранить доступ к данным после удаления исходного имени файла. Символическая ссылка зависит от существования целевого пути. Git позволяет восстановить содержимое удалённого файла, однако для восстановления жёсткой связи необходимо повторно выполнить команду ln.

Первоначальная гипотеза полностью подтвердилась.


## Задание 5. Исследование прав доступа

### Цель

Изучить права доступа к файлам Linux и научиться изменять их с помощью команды chmod.

### Гипотеза

Предполагаю, что:

- Без права выполнения файл hello.sh нельзя запустить напрямую.
- После добавления права выполнения программа успешно запустится.
- С помощью chmod можно ограничить доступ других пользователей к файлу.
- Изменение прав доступа не изменяет содержимое файла.

### Эксперимент
Для исследования прав доступа был создан Bash-скрипт hello.sh.

Выполнены следующие команды:

```bash
printf '#!/bin/bash\necho "Hello, Linux!"\n' > hello.sh
cat hello.sh
chmod 644 hello.sh
ls -l hello.sh
./hello.sh
chmod u+x hello.sh
ls -l hello.sh
./hello.sh
chmod 750 hello.sh
ls -l hello.sh
stat hello.sh
printf 'secret.txt\ndisk.img\nworkspace/private/\n' >> .gitignore
echo "Confidential information" > secret.txt
chmod 600 secret.txt
ls -l secret.txt
git check-ignore secret.txt
```

### Наблюдение

После установки прав 644 попытка запуска скрипта завершилась ошибкой Permission denied.

После выполнения команды chmod u+x hello.sh скрипт успешно запустился и вывел сообщение Hello, Linux!

Затем были установлены права 750.

| Характеристика | Значение |
|---|---|
| Имя файла | hello.sh |
| Inode | 21477 |
| Размер | 33 байта |
| Blocks | 8 |
| Количество жёстких ссылок | 1 |
| Итоговые права | 0750 |
| Символьная запись | -rwxr-x--- |

Дополнительно был создан файл secret.txt размером 25 байт. Для него установлены права 600, разрешающие чтение и запись только владельцу.

Команда git check-ignore secret.txt подтвердила, что данный файл игнорируется Git.

### Объяснение

В Linux используются три основных права доступа:

- r (4) — чтение;
- w (2) — запись;
- x (1) — выполнение.

Права 750 означают:

- Владелец: чтение, запись и выполнение (4 + 2 + 1 = 7).
- Группа: чтение и выполнение (4 + 1 = 5).
- Остальные пользователи: доступ запрещён (0).

Права 600 означают, что только владелец может читать и изменять файл.

Ошибка Permission denied возникла из-за отсутствия права выполнения у скрипта. После добавления этого права ошибка исчезла.

Файл .gitignore используется для исключения конфиденциальных и ненужных файлов из числа файлов, добавляемых в Git.

### Вывод

В ходе эксперимента я научился просматривать и изменять права доступа к файлам Linux. Установлено, что корректное содержимое скрипта не гарантирует возможность его прямого запуска без соответствующего разрешения. С помощью chmod можно управлять доступом владельца, группы и остальных пользователей. Также был настроен файл .gitignore для предотвращения случайной публикации конфиденциальных данных.

Гипотеза подтвердилась.


## Задание 6. Кейс «Почему один файл сохранился, а другой исчез?»

### Цель

Изучить процесс создания, монтирования и размонтирования файловых систем ext4 и tmpfs.

### Гипотеза

Предполагаю, что:

- Файл, записанный в файловую систему ext4, сохранится после размонтирования и повторного подключения.
- Файл, записанный в tmpfs, исчезнет после размонтирования, поскольку эта файловая система предназначена для временного хранения данных.
- Доступное пространство ext4 будет меньше размера виртуального диска, поскольку часть пространства используется для служебной информации файловой системы.

### Эксперимент
Для исследования был создан виртуальный диск disk.img размером 50 МиБ и файловая система ext4.

#### Исследование ext4

Выполнены команды:

```bash
dd if=/dev/zero of=disk.img bs=1M count=50
ls -lh disk.img
git check-ignore disk.img
mkfs.ext4 -F disk.img
mkdir -p mnt
sudo mount -o loop disk.img mnt
df -hT mnt
findmnt mnt
sudo chown "$(id -u):$(id -g)" mnt
echo "Файл на ext4" > mnt/note.txt
cat mnt/note.txt
sudo umount mnt
ls -la mnt
sudo mount -o loop disk.img mnt
cat mnt/note.txt
sudo umount mnt
```

При создании файловой системы получены следующие результаты:

| Характеристика | Значение |
|---|---|
| Размер виртуального диска | 50 МиБ |
| Количество блоков | 12800 |
| Размер блока | 4096 байт |
| Количество inode | 12800 |
| Размер журнала | 1024 блока |
| Устройство | /dev/loop0 |
| Тип файловой системы | ext4 |
| Размер по df | 43 МиБ |
| Занято | 152 КиБ |
| Доступно | 40 МиБ |
| Использование | 1% |

После первого монтирования был создан файл note.txt. После размонтирования каталог mnt стал пустым. При повторном монтировании файл снова стал доступен, а его содержимое сохранилось.

#### Исследование tmpfs

Выполнены команды:

```bash
mkdir -p ram
sudo mount -t tmpfs -o size=10m tmpfs ram
df -hT ram
findmnt ram
sudo chown "$(id -u):$(id -g)" ram
echo "Файл в tmpfs" > ram/note.txt
cat ram/note.txt
sudo umount ram
sudo mount -t tmpfs -o size=10m tmpfs ram
ls -la ram
sudo umount ram
findmnt mnt
findmnt ram
```

Была создана временная файловая система tmpfs с ограничением размера 10 МиБ. В неё записан файл note.txt.

После размонтирования и повторного монтирования каталог ram оказался пустым. Созданный ранее файл не сохранился.

### Наблюдение

| Вопрос | ext4 | tmpfs |
|---|---|---|
| Где хранятся данные? | В образе виртуального диска disk.img | В оперативной памяти и при необходимости в swap |
| Сохранился ли файл после umount? | Да | Нет |
| Почему? | Данные записаны в постоянное хранилище | При размонтировании временная файловая система уничтожается |

Команды findmnt mnt и findmnt ram не вывели результатов, что подтверждает успешное размонтирование обеих файловых систем.

### Ответы на дополнительные вопросы

**1. Почему размер доступного пространства ext4 меньше размера disk.img?**

Часть пространства используется для хранения служебной информации: журнала, таблиц inode, суперблоков и других метаданных. Также часть блоков резервируется файловой системой.

**2. Что такое точка монтирования?**

Точка монтирования — это каталог, через который пользователь получает доступ к подключённой файловой системе. В данном эксперименте использовались каталоги mnt и ram.

**3. Что произойдёт, если попытаться размонтировать файловую систему, когда процесс использует находящийся в ней файл?**

Обычная команда umount завершится ошибкой Target is busy, поскольку файловая система ещё используется. Необходимо завершить работу с открытыми файлами и повторить размонтирование.

**4. Что произойдёт, если удалить disk.img, пока он смонтирован? Сохранятся ли данные после размонтирования?**

Имя файла disk.img исчезнет из каталога, но loop-устройство может продолжать удерживать открытый файл. Поэтому данные могут оставаться доступными до размонтирования. После освобождения loop-устройства, если других ссылок на образ нет, его данные будут освобождены. Повторно подключить образ по прежнему имени не получится.

### Вывод

В ходе эксперимента я научился создавать виртуальные диски, форматировать их и монтировать файловые системы. Установлено, что ext4 обеспечивает постоянное хранение данных, а tmpfs предназначена для временного хранения. После повторного подключения ext4 файл сохранился, а после повторного подключения tmpfs файл отсутствовал. Также было установлено, что часть пространства ext4 используется для служебной информации файловой системы.

Первоначальная гипотеза полностью подтвердилась.


## Контрольные вопросы

**1. Чем имя файла отличается от inode?**

Имя файла позволяет пользователю найти файл в каталоге. Inode хранит информацию о файле: размер, владельца, права доступа и расположение данных на диске.

**2. Почему после mv номер inode обычно остаётся прежним?**

При переименовании в пределах одной файловой системы изменяется запись в каталоге, а сам файл и его данные остаются прежними. В моём эксперименте номер inode 20980 не изменился.

**3. Почему два файла могут иметь одинаковый inode?**

Это происходит при создании жёсткой ссылки. Два разных имени указывают на один файл. В моём эксперименте report.txt и backup.txt имели общий inode 21510.

**4. Почему после git restore жёсткая связь не восстанавливается автоматически?**

Git сохраняет содержимое файлов, но не отношения жёстких ссылок между ними. При восстановлении создаётся отдельный файл с новым inode. Для восстановления жёсткой связи необходимо использовать команду ln.

**5. Почему символическая ссылка может стать битой?**

Символическая ссылка хранит путь к целевому файлу. Если файл удалить или переместить, ссылка больше не сможет найти его по указанному пути.

**6. Почему файл нельзя запустить, даже если его содержимое корректно?**

У пользователя может отсутствовать право выполнения файла. В моём эксперименте скрипт hello.sh с правами 644 не запускался. После выполнения chmod u+x hello.sh скрипт успешно запустился.

**7. Какие права нужны для удаления файла из каталога?**

Обычно необходимы права записи (w) и прохода (x) для родительского каталога. Право записи в сам файл необязательно. Дополнительные ограничения, например sticky bit, также могут влиять на удаление.

**8. Что означает chmod 750?**

Владелец может читать, изменять и выполнять файл. Группа может читать и выполнять файл. Остальные пользователи не имеют доступа.

- 7 = 4 + 2 + 1 — чтение, запись и выполнение.
- 5 = 4 + 1 — чтение и выполнение.
- 0 — отсутствие прав.

**9. Почему ext4 сохраняет данные после размонтирования, а tmpfs — нет?**

Ext4 хранит данные на постоянном носителе, а tmpfs использует оперативную память и при необходимости swap. После размонтирования tmpfs её содержимое теряется.

**10. Почему номер inode недостаточен для однозначного определения файла среди всех файловых систем?**

Номер inode уникален только внутри конкретной файловой системы. На разных устройствах могут существовать файлы с одинаковыми номерами inode. Поэтому необходимо учитывать также идентификатор устройства.

**11. Что произойдёт с удалённым файлом, если процесс продолжает держать его открытым?**

Имя файла исчезнет из каталога, но процесс сможет продолжать работать с его содержимым через открытый файловый дескриптор. Данные будут освобождены после закрытия последнего дескриптора, если других ссылок на файл нет.

**12. Почему Git не должен содержать secret.txt и disk.img?**

Файл secret.txt может содержать конфиденциальную информацию, которую нельзя публиковать. Disk.img является большим двоичным файлом виртуального диска, который не требуется хранить в Git. Для исключения этих файлов используется .gitignore.
